Resumen Ejecutivo

ControlesTaleiro es un sistema empresarial completo de gestión de recursos humanos, activos y seguridad laboral orientado al sector de construcción y mantenimiento. Construido sobre Laravel 12 + Livewire 4 + Flux 2.9, el proyecto lleva aproximadamente 1 mes de desarrollo activo con 70 migraciones y múltiples interfaces: escritorio web, aplicación móvil PWA, panel de TV y monitor de estadísticas.

Laravel 12 Livewire 4 Flux 2.9 Tailwind CSS 4 PHP 8.2+ SQLite / MySQL Maatwebsite Excel Laravel Fortify PWA Ready 2FA

El proyecto es un MVP muy completo con funcionalidades avanzadas bien pensadas (firmas digitales polimórficas, auditoría de sesiones, roles granulares, importación/exportación Excel). Sin embargo, necesita hardening antes de entrar en producción, especialmente en persistencia de datos, concurrencia y cobertura de tests.

Problemas estructurales detectados

A) Lógica de negocio mezclada en Livewire

Componentes como PhoneDisplay.php (~30KB) y GestaoEquipas.php mezclan lógica de presentación con reglas de negocio. A medida que crezca, serán inmantenibles y difíciles de testear.

// Problema: todo en el componente Livewire
// PhoneDisplay.php = 30KB, GestaoEquipas.php = cientos de líneas

// Solución: extraer a Services/Actions
app/Services/
├── EpiStockService.php         // lógica de stock
├── AtribuicaoService.php       // planificación equipas
├── GuiaTransporteService.php   // guías de transporte
└── SignatureService.php        // firmas digitales

B) ORDEM_PREDEFINIDA con IDs hardcodeados

Los IDs de base de datos en el código fuente son frágiles: romperán silenciosamente si la DB se resetea o migra a producción.

// Actual — FRÁGIL
const ORDEM_PREDEFINIDA = [1, 3, 7, 12, 2, 18, 20, 13, 6, 4, 8, 14, 21, 5, 9, 15, 10, 19];

// Solución: agregar campo `ordem` a tabla peps
// y ordenar por Pep::orderBy('ordem')->get()

C) Sin capa de Services/Actions

No existe la carpeta app/Services/ ni app/Actions/ (excepto los de Fortify). Toda la lógica de negocio está dispersa entre modelos y componentes Livewire.

Escalabilidad

Análisis de los puntos que limitarán el crecimiento del sistema bajo carga real de producción.

Área de Riesgo Descripción del Problema Criticidad
SQLite en producción SQLite no soporta escrituras concurrentes. Con varios usuarios simultáneos, habrá errores de bloqueo de base de datos. ALTA
Firmas base64 en DB Cada firma digital puede ocupar 50–200KB en longtext. Con 1.000 entregas = hasta 200MB solo en firmas. Degrada enormemente el rendimiento de queries. ALTA
Race condition en stock EPI Decrementar stock_total sin transacción atómica permite que dos usuarios simultáneos entreguen el mismo último artículo. ALTA
PhoneDisplay polling 20s Con 50+ usuarios móviles activos, el servidor recibirá 150 requests/minuto solo de actualizaciones de pantalla. Sin caché, cada uno ejecuta N queries. MEDIA
Exports Excel síncronos Generar un Excel grande (ferramentas + logs, colaboradores + estadísticas) puede tardar 10–30 segundos, bloqueando el proceso PHP del usuario. MEDIA
Sin caché en datos estáticos Listas de PEPs, colaboradores, locaciones se consultan en cada request aunque cambien poco. Oportunidad clara de caché. MEDIA
SignatureRequests sin limpieza Tokens expirados nunca se eliminan. La tabla crece indefinidamente, especialmente con uso intensivo de firmas móviles. MEDIA
Sin índices en todas las FK Algunas migraciones posteriores pueden carecer de índices en columnas de búsqueda frecuente (e.g. colaborador_id en EPI entregas). BAJA
⚠
Migración SQLite → MySQL es obligatoria antes de producción El .env.example usa DB_CONNECTION=sqlite. Las migraciones son compatibles con MySQL, pero hay que verificar columnas longtext y el comportamiento de campos JSON antes de migrar.

Errores y Bugs Potenciales

Bug #1 — Race Condition en Stock EPI

⚠
Criticidad: Alta | Afecta: EpiEntregas/Form.php Si dos usuarios entregan el último artículo simultáneamente, el stock puede quedar negativo sin que el sistema lo detecte. 
// PROBLEMA ACTUAL
EpiItem::where('id', $id)->decrement('stock_total');

// SOLUCIÓN: DB::transaction + lockForUpdate
DB::transaction(function() use ($id, $cantidad) {
    $item = EpiItem::lockForUpdate()->findOrFail($id);
    if ($item->stock_total < $cantidad) {
        throw new \Exception('Stock insuficiente');
    }
    $item->decrement('stock_total', $cantidad);
});

Bug #2 — IDs hardcodeados en ORDEM_PREDEFINIDA

!
Criticidad: Media | Afecta: GestaoEquipas.php Los IDs [1, 3, 7, 12, 2, 18...] son IDs de base de datos. En producción, después de un migrate:fresh o una migración real, estos IDs no corresponderán a los PEPs correctos y el orden será incorrecto sin error visible.

Bug #3 — SignatureRequests sin limpieza automática

!
Criticidad: Media | Afecta: signature_requests tabla Los tokens expirados (>24h) nunca se eliminan. La tabla acumulará registros inactivos indefinidamente. 
// Solución: Command artisan + schedule diario
// app/Console/Commands/CleanExpiredSignatures.php
SignatureRequest::where('status', 'expired')
    ->where('expires_at', '<', now()->subDays(30))
    ->delete();

// routes/console.php
Schedule::command('signatures:cleanup')->daily();

Bug #4 — Polling sin manejo de sesión expirada

!
Criticidad: Media | Afecta: PhoneDisplay.php El poll(20000ms) continúa después de que la sesión del colaborador expire, generando requests de error silenciosos en bucle que consumen recursos del servidor.

Bug #5 — Importadores sin validación robusta

!
Criticidad: Media | Afecta: app/Imports/* Si el Excel subido tiene formato incorrecto, columnas faltantes o tipos de datos erróneos, puede crear registros inválidos silenciosamente. Verificar que todos los Imports implementen WithValidation.

Bug #6 — Sin tests de regresión

⚠
Criticidad: Alta (a largo plazo) Los directorios tests/Feature/ y tests/Unit/ están esencialmente vacíos. Cualquier refactor futuro puede romper flujos críticos (stock, firmas, entregas) sin que el sistema lo detecte automáticamente.

Mejoras Prioritarias

Prioridad Alta — Antes de producción

A) Migrar a MySQL/PostgreSQL

  • SQLite no soporta concurrencia real
  • Cambiar DB_CONNECTION=mysql
  • Verificar compatibilidad de migraciones
  • Impacto: elimina bloqueos concurrentes

B) Firmas en storage, no en DB

  • Guardar base64 en storage/app/signatures/
  • Solo guardar la ruta en DB
  • Reducción drástica del tamaño de DB
  • Queries de consulta 10x más rápidas

C) Transacciones en stock EPI

  • Wrappear entregas/devoluciones en DB::transaction
  • Usar lockForUpdate() en EpiItem
  • Validar stock antes de decrementar
  • Previene stock negativo por concurrencia

D) Tests críticos básicos

  • Test de flujo EPI (entrega, devolución, stock)
  • Test de firmas digitales
  • Test de validación de importadores
  • Test de acceso por roles

Prioridad Media — Próximas 2–4 semanas

E) Capa de Services/Actions

  • Crear app/Services/
  • Extraer lógica de Livewire components
  • Facilita testing y reutilización

F) Exports asíncronos con Queue

  • Dispatch jobs de Excel a queue
  • Notificar al usuario cuando esté listo
  • Evita timeouts en exports grandes

G) Caché para datos estáticos

  • PEPs, colaboradores, locaciones
  • Cache::remember('peps', 3600, ...)
  • Invalidar al crear/editar

H) Orden dinámica de PEPs

  • Campo ordem en tabla peps
  • UI drag-and-drop para reordenar
  • Eliminar IDs hardcodeados del código

Prioridad Baja — Mejoras de calidad

I) Rate limiting en rutas móviles

  • Throttle en PhoneDisplay
  • Proteger endpoints de importación

J) Notificaciones automáticas

  • Email cuando EPI en stock crítico
  • Mail a Logi cuando verificación vencida
  • Job diario de verificación

K) Limpieza de tokens expirados

  • Command + Schedule diario
  • Eliminar SignatureRequests >30 días

L) Logging mejorado

  • Log de operaciones críticas de stock
  • Log de importaciones con resultados
  • Alertas de errores en exports

Deuda Técnica

Resumen de la carga técnica acumulada que deberá abordarse para garantizar la salud a largo plazo del proyecto.

Alta SQLite en uso — No apto para producción con múltiples usuarios concurrentes. Requiere migración a MySQL antes del lanzamiento.
Alta Firmas base64 en base de datos — Crecimiento exponencial del tamaño de DB. Mover a storage/ con urgencia.
Alta Sin transacciones en operaciones de stock — Race condition real en uso concurrente de entregas de EPIs.
Alta Sin cobertura de tests — Tests Feature y Unit prácticamente vacíos. Todo cambio futuro es un riesgo no controlado.
Media PhoneDisplay.php monolítico — Componente de 30KB con lógica de negocio mezclada. Difícil de mantener y testear.
Media Exports Excel síncronos — Bloquean el proceso PHP. Deben moverse a queues con notificación al usuario.
Media Sin capa de Services — Lógica de negocio dispersa en componentes Livewire. Dificulta reutilización y testing.
Media Polling sin gestión de sesión expirada — PhoneDisplay puede generar errores silenciosos en bucle tras expirar la sesión.
Baja IDs hardcodeados en ORDEM_PREDEFINIDA — Frágil ante resets de DB o migración a producción.
Baja Sin caché para datos estáticos — PEPs, locaciones y colaboradores consultados en cada request sin necesidad.
Baja SignatureRequests sin limpieza automática — Tokens expirados acumulados indefinidamente en la tabla.
